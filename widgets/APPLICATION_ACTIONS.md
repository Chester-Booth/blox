# Application action integration

Command bindings have one owner. Ordinary `run` bindings stay with the command provider. `launch` and the exact first-party `blox-widget-action todo edit` and `blox-widget-action calendar open` run bindings go to `WidgetActionController`. It resolves the current enabled widget and binding. The view supplies only button identity. The Python helper validates the captured complete widget structurally and resolves its binding again. It never executes payload argv.

The controller starts no command launch until its fixed `validateCommandHost` callback returns exactly true. It checks the current profile after that callback, because the callback can re-enter application code. It repeats both checks when the helper starts, before writing a request to stdin. A stale helper receives no launch request and is terminated. The controller serialises startup and has no retry queue. Timeout means an uncertain handoff. Completion results retain the command identity in `result.identity`.

## Root hooks

DesktopWidgets and shell.qml now connect these hooks. They use the originating output workspace and exact consumer identity.

1. Set each host's reserved `trustedLaunchContext` from that output's captured workspace. Copy exactly `{outputName: screen.name, workspace: {id: workspace.id, name: workspace.name, special: workspace.special}}`. Do not derive it from focused workspace, widget settings, view payloads or stdout. This field is separate from the view context and saved profile. Keep host `workspace` and this context bound to the same output workspace.
2. Connect `host.applicationActionRequested(action, identity, trustedContext)` to `widgetActions.dispatch(identity.widgetId, action, identity, trustedContext)`. This is the command launch execution signal. `host.actionRequested` remains observational for commands. Keep the existing application routing for other kinds.
3. Set `widgetActions.validateCommandHost` to a fixed application function. Locate the exact host by `identity.consumerId`, then return `host.isCurrentAction(identity, trustedContext)`. An absent host returns false. Do not resolve a replacement host by widget ID alone. The method checks subscription identity, generation, visibility, edit state, configuration and the captured reserved context. The controller independently checks the current enabled application profile.
4. Connect the application-owned finite workflow hooks described below.
5. Connect `host.focusReleaseRequested()` to the application's keyboard widget focus owner. Clear ownership only if that exact host still owns it. The host already releases the view's focus. No keyboard focus is acquired automatically.

For launch completion, `actionFinished(widgetId, action, result)` includes `{widgetId, consumerId, generation, button}` in `result.identity`. Check that identity against the current host before attaching feedback to a visible widget. A result is never an instruction to replay an action.

`DesktopWidgets.validateCommandHost` resolves one registered consumer, rejects application editing, then checks the host and its originating output/workspace. `dispatchApplicationAction` checks that the sender is that registered host before forwarding. `releaseHostKeyboardFocus` releases only the exact keyboard owner through the existing guarded previous-app restoration route. The fallback, restart, mask, fullscreen and queued-focus guards remain intact.

`tests/qml/tst_CommandApplicationIntegration.qml` executes the production DesktopWidgets functions and delegate handlers, shell callbacks and origin binding against a real host and fake process. `tst_WidgetActionController.qml` checks profile mutation, callback re-entry and rejection before the request is written.

## Application-owned GUI workflows

The exact three-element command argv `blox-widget-action todo edit` and `blox-widget-action calendar open` remain schema-valid `run` records. They have application lifetime because opening the GUI can hide the originating widget before placement or refresh finishes. This changes the hide rule in the original interaction contract for these two fixed operations only, accepted on 25 October 2026, including indistinguishable unrelated occupancy and workspace-1 transitions. Custom commands and both selection actions retain consumer lifetime and cancel on unsubscribe.

The controller validates the host before startup and again before writing the request. `beginCommandWorkflow(identity, context)` then calls that exact host's `beginApplicationWorkflow`. The host requests producer unsubscription and holds the accepted workflow identity separately from its reveal generation. The provider adapters correlate the existing broker unsubscribe acknowledgement, which follows provider close and reaping. Only that matching acknowledgement releases helper input. Local subscription deletion does not confirm teardown. A three-second cancellation-aware wait bounds this prerequisite. Failure, lost transport, stale acknowledgements and cancellation cannot release input or trigger a retry. No new producer or activation starts until `finishCommandWorkflow(identity)` releases that identity after process exit and stdout EOF. Completion refreshes an eligible host once. A hidden host stays unsubscribed. A later reveal starts fresh without replaying the action.

`applicationWorkflowReady(identity)` connects the matching teardown acknowledgement through DesktopWidgets to `widgetActions.workflowReady(identity)`. `applicationWorkflowCancelled(identity)` connects the host through DesktopWidgets to `widgetActions.cancelWorkflow(identity)`. Explicit host refresh, explicit hiding, edit mode, provider/output replacement, widget configuration change and host destruction cancel. The controller independently cancels if the current enabled widget no longer matches the captured full configuration. A cancelled identity remains busy until teardown completes. Normal QML property notifications drive configuration checks. In-place edits without notification are checked at action boundaries, as elsewhere in the host API.

The narrow visibility exemption permits Todo's source workspace to become occupied and permits calendar to focus workspace 1. Other workspace changes cancel. These predicates cannot attribute an occupied-workspace event to a particular window. A concurrent unrelated window on the source workspace is indistinguishable during the bounded workflow. Todo still requires the launched window's new address, launch ID, PID, workspace and final geometry to match before success. Calendar refresh still follows launch and workspace-1 focus, including launch/focus failures. It never claims verified browser placement.

The controller invokes `action.py --workflow <applicationPid>`, which accepts only these two exact run operations and resolves `user_actions.py` from the same source/installed tree. It cannot background arbitrary configured argv. `OwnedInvocation` uses the service-main supervisor to own the entire finite invocation cgroup, bounds combined output to 1 MiB, and requires direct exit, pipe EOF and confirmed cgroup cleanup. Todo's cap is at most 10 seconds and calendar's at most 120, or the binding's smaller cap. The controller has a further three-second startup/teardown allowance. TERM/KILL, timeout, output overflow, normal completion and application death kill the finite invocation cgroup. The application supplies `Quickshell.processId` as a separate workflow runner argument. After installing its Linux parent-death guard, the runner checks that its current parent still equals that expected application PID. Adoption by a subreaper during interpreter startup therefore fails before reading buffered input. The service-main supervisor watches this runner by pidfd and kills its invocation after runner death. Only the helper's existing compositor GUI handoff is independent. No idle workflow process, service, queued action or automatic mutating retry exists.

The broker wire protocol, profile schema and saved configuration do not change. Provider adapters now forward the existing unsubscribe acknowledgement for application workflow gating. The workflow hook is application-owned, separate from the SDK view context API. `tests/qml/tst_CommandApplicationIntegration.qml` exercises the production host/application hooks offscreen. `widgets/tests/test_action_lifetime.py` uses a copied source tree, temporary data and a fake compositor to reproduce old cancellation and verify new completion, refresh failure, timeout, cancellation and application death. Its lasting synthetic GUI has an explicit test owner and always gets reaped.

## Trusted finite context

The host copies context before observation callbacks. For run bindings it passes the copy as the optional fifth argument to `dispatchAction(consumerId, action, payload, generation, hostContext)`. NativeProvider and QuickshellBroker forward it as top-level `hostContext`, outside payload and settings. The stdio broker belongs to the application. View code cannot access that channel through its context API.

Before forwarding, the host checks that captured context still matches its originating workspace, including nested changes without notification. The broker then checks the current consumer generation. CommandOutput validates and copies host context before admitting an action. OwnedInvocation strips inherited/configured `BLOX_WIDGET_ACTION_CONTEXT`, then sets it only for that finite action to `{"workspaceId":4}`. Producers, completion refreshes and reconnect subscriptions never inherit it. Configured content/run environments still reject the reserved key. Action stdout is drained as data and never becomes context.

The context validator requires a nonempty output name of at most 256 UTF-8 bytes and exactly `workspace.id`, `workspace.name` and `workspace.special`. Supported workspaces have positive integer IDs, the matching decimal name and `special: false`. Named and special identities return `unavailable`, including through broker action results. Missing context cannot fall back to desktop focus. Custom run actions without context still work; first-party operations that require placement reject missing context.

The launcher makes one compositor execution request for captured numeric workspaces. Nonzero dispatch, missing dispatcher and timeout never fall back to an unplaced process. It quotes every argv element and removes reserved context from the compositor child environment. Intentional GUI work belongs to the compositor after acceptance. Ordinary finite children remain inside the invocation cgroup and its mandatory containment namespace. The output name records origin; it does not establish multi-monitor window geometry. Browser reuse still prevents a verified browser placement claim.

## New bindings and packaging

`blox_widgets.first_party.todo_calendar_profile(script_root)` returns a new complete schema-valid profile. Its producer argv use an explicit absolute installed `shell/scripts` directory. Its four bindings use the installed command name.

| Widget | Button | Argv | Cap in seconds |
| --- | --- | --- | --- |
| Todo | Left | `blox-widget-action todo next` | 5 |
| Todo | Right | `blox-widget-action todo edit` | 10 |
| Calendar | Left | `blox-widget-action calendar next` | 120 |
| Calendar | Right | `blox-widget-action calendar open` | 120 |

All four are finite `run` records, with empty cwd and environment. Editing and calendar opening include an intentional GUI handoff inside the finite workflow. The independently reviewed helper preserves selection ordering, lock release before generated refresh, and launch then workspace-1 focus then calendar refresh. Completion refresh remains the execution owner's responsibility, including after failure. No existing user data or frozen profile is read or rewritten by the builder. `examples/first-party-actions.profile.json` is synthetic. Root must use the existing Apply transaction later.

The current installer copies `bin`, `shell` and `widgets` and registers `blox-widget-action` in `INSTALLED_BINS`. This packages the executable wrapper, `user_actions.py`, `action.py`, launcher module and widget Python/schema dependencies together. Installed-layout tests materialise only installer-enumerated files in a temporary prefix, invoke the copied wrapper and import/validate from that copied tree in isolated Python mode. They do not run the installer.

System dependencies remain system dependencies. Python 3 with PyGObject/GioUnix, Hyprland's `hyprctl`, Kitty and Micro are needed for editing. Zen and gcalcli support calendar open/generation. Curl is needed when expense exports are configured. Notify-send handles the intentional authentication notification. Missing tools return helper failure. No utility is installed by this change. A user bundle only discovers executable argv heads. A command name is not a packaged transitive dependency closure.

Native pointer/keyboard/rendering, real compositor placement, browser reuse, live calendar refresh and installed runtime acceptance remain unverified. No complete Todo/calendar parity claim follows from the offline checks.

The service-main process is now the ownership supervisor. Actual Qt-child IPC discovery, failure bounds, safety policy and offline/live limits are specified in `OWNERSHIP.md`. Missing delegation or namespace setup does not enable a weaker owner.
